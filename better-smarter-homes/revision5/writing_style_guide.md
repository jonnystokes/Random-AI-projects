# Revision 5 Writing Style Guide

Last updated: 2026-05-08

## Purpose

This file defines the writing rules for Revision 5.

The book is a technical owner-builder manual for a concrete home in Oregon. It serves the person doing the work, a curious non-builder reading along, and the builders, designers, engineers, inspectors, and suppliers who will hold serious conversations about the project.

The writer's stance is calm and informed. The prose explains construction work in plain language with real specifics. It treats the reader as a capable adult. It does not scold, posture, perform, or dramatize.

This file is also a writing sample. It demonstrates the voice it asks for. If a sentence in this file would fail one of its own rules, the rule wins and the sentence is wrong.

## Core Voice

Plain. Specific. Technically grounded.

Use ordinary words first. Use trade words when they add precision. State facts directly. When a problem exists, name the problem and state the next step.

Warmth comes from two sources only: respect for the reader, and concrete detail about the work. Warmth does not come from emotional language, decorative phrasing, voice imitation, or any attempt to make the prose sound impressive.

Readable does not mean clever, jolly, whimsical, sentimental, dramatic, or quotable. Readable means the next sentence is easy to follow because the previous one was clear and exact.

## First Person

The default voice is impersonal. The book is a manual, not a memoir.

First person is allowed where it carries the project's perspective and earns its place. Examples that fit: a brief origin statement at the start of Chapter 1, an occasional design-rationale note that names the owner's specific choice ("I chose mineral wool here because…"), and other passages where the impersonal voice would be evasive or hide a real decision.

First person does not belong in technical procedures, parameter discussions, code citations, inspection-readiness lists, or routine description. When the choice is between a clean impersonal sentence and a forced first-person sentence, write impersonal.

Do not manufacture first-person passages to add warmth. Use it where it actually fits.

## Absolute Rule: No Metaphor

Plain literal description is the default everywhere in the book, in every layer. Metaphor is allowed only when the figure is precise and the literal version is much longer or unavailable.

This rule is strictest in `Simple`. Plain prose for non-builders does not need metaphor to be readable. Specifics, exact nouns, and short sentences carry the load. A `Simple` block that reaches for a metaphor is almost always reaching for the wrong tool.

The same rule applies in `Applied`, `Professional`, and `Code`. If a sentence depends on a figure of speech, rewrite the sentence around what is actually happening.

## Absolute Rule: No Personification

Inanimate things do not have intentions, feelings, opinions, preferences, demands, votes, interests, personalities, or human actions. They do not tell, ask, demand, want, need (in the emotional sense), argue, agree, fight, resist, welcome, invite, care, stay interested, or carry burdens.

This applies to the book, manuscript, chapter, house, property, site, land, soil, materials, systems, code, weather, water, concrete, tools, drawings, details, assemblies, forms, inspections, records, and every other inanimate noun.

Technical verbs are fine when they describe real physical behavior. Concrete walls resist fire. Soil supports the footing. Flashing directs water to the exterior. Drawings document the approved detail. The test is whether the verb describes a measurable physical action or a human-style intention.

| Bad | Better |
|---|---|
| I have carried this house around for about ten years. | I have wanted to build this house for about ten years. |
| The book turns the idea into something that can be argued with. | The book records the idea as information that can be checked, revised, and built. |
| The property has to work with zoning. | The design must comply with zoning. |
| The site is telling you to change the footprint. | The test results show that the footprint should change. |
| Water wants to get into the wall. | Water enters the wall through cracks, gaps, and unsealed penetrations. |
| Code welcomes creative ideas. | The building official can approve compliant alternative methods. |
| The soil disagrees with the design. | The soil report shows bearing values below what the design assumes. |

If a sentence gives an inanimate subject a human action, rewrite around the actor, mechanism, condition, or decision.

## Absolute Rule: No Rhetorical Performance

The book is a technical reference. It is not an essay, opinion column, magazine feature, motivational speech, or branded marketing piece. The writer must not use the rhetorical tools that performative writing reaches for.

The patterns below are forbidden. They are forbidden even when the writer can produce them well. The goal is plain technical prose, not crafted prose.

### Aphoristic closers

Short, polished sentences that exist to feel quotable. Often appear at the end of sections, paragraphs, or chapters.

| Bad | Better |
|---|---|
| Never bury a code question in concrete. | Resolve code questions before placing concrete. Once concrete cures, exposing and correcting an error becomes expensive. |
| The land gets a vote. | The site conditions affect what can be built. |
| Build the hard parts so they can stay. Route the service parts so they can change. | Design the foundation and structure for long service. Design the mechanical, electrical, and plumbing systems for access and replacement. |

### Antithesis ("X is not A. It is B.")

Two-sentence contrasts that frame a point as a reveal.

| Bad | Better |
|---|---|
| Inspections are not interruptions. They are checkpoints. | Inspections are scheduled checkpoints in the build sequence. |
| Code is not a barrier. It is the approval path. | Code defines the approval path for the project. |
| The owner-builder path is not a loophole. It is a legal role. | The owner-builder path is a legal role with specific duties. |

### Definition by negation

Telling the reader what something is not before saying what it is. Wastes the reader's time.

| Bad | Better |
|---|---|
| Code is not a wall. It is a map. | Code is the rule system that controls what must be submitted, reviewed, built, inspected, and approved. |
| These principles are not decoration. They make decisions. | These principles guide design choices when two options would both work. |

### Rule of three and rhetorical triplets

Three-item lists used for cadence rather than information.

| Bad | Better |
|---|---|
| Lights should still turn on. Heat should still work. Doors should still lock. | Basic functions (lighting, heating, door locks) should continue to operate when the internet is unavailable. |
| It is land, tools, concrete, weather, math, comfort, code, systems, and imagination brought into one build. | The project combines site work, structural concrete, code compliance, mechanical systems, and design choices into one build. |

If three items are the actual count, three is fine. If three was chosen for rhythm, cut to two or expand to a real list.

### Anaphora (repeated sentence openings for cadence)

| Bad | Better |
|---|---|
| Roof surfaces wear out. Sealants crack. Windows age. Plumbing parts fail. Electrical gear changes. | Roof surfaces, sealants, windows, plumbing parts, and electrical equipment all reach end of service life on shorter cycles than the structure. |

If the parallel structure is genuinely useful (a checklist, a procedure), keep it. If it exists for rhythm, replace with a single clear sentence.

### Persuasive headings

Section titles must name the topic. They must not make claims, frame arguments, or sound clever.

| Bad | Better |
|---|---|
| Code Is A Map, Not A Wall | The Oregon Code System |
| Owner-Builder Reality Belongs In The Code Map | Owner-Builder Role |
| The Long-Life Home | Long-Service Design |

### Blockquote callouts as pronouncements

Blockquote callouts are reserved for verbatim quotation of code, standards, or other source material. They are not for elevating sentences the writer thinks are important.

If a rule matters, write it as a normal sentence in normal prose. If it matters enough to set apart, make it a numbered list item or a definition.

### Decorative intensifiers

Words that add color but no information. Cut them.

Forbidden: truly, deeply, profoundly, remarkably, beautifully, simply, really, actually, very, quite, rather, somewhat, fairly, the real, the actual.

| Bad | Better |
|---|---|
| The real long-life target is the skeleton. | The long-life target is the structural skeleton. |
| The long-life target is simple and ambitious. | The long-life target applies to the parts that are difficult to replace. |

### Compound serial lists for completeness signaling

Long comma-separated noun strings that exist to signal "we covered everything." Pick a real list with a real reason for each item, or write a sentence.

| Bad | Better |
|---|---|
| It is land, tools, concrete, weather, math, comfort, code, systems, and imagination brought into one place. | The project includes site work, structural concrete, mechanical systems, and code compliance. |
| concrete walls, local smart-home control, service routes, Oregon code, owner-builder rules, plumbing, electrical, soil, inspection, testing, future repair, and all the small decisions that make or break a house | the structural shell, mechanical and electrical systems, code compliance, and inspection sequence |

### Persuasive openers

Section and chapter openings must state the topic. They must not deliver a thesis sentence designed to set the rhetorical frame.

| Bad | Better |
|---|---|
| I have carried this house around for about ten years. | I have wanted to build a long-lasting concrete home in Oregon for about ten years. This book is the plan. |
| Code is not a barrier to an unusual house. It is the approval path that lets an unusual house be permitted, inspected, documented, and sold later without avoidable disputes or hidden defects. | This chapter describes the Oregon code system as it applies to this project. |

### Concession-then-correction

"X. But Y." or "That does not make the goal smaller. It makes it buildable." These are rhetorical pivots that perform balance.

If the second sentence is the real point, write only the second sentence. If both sentences carry information, separate them as plain claims.

### Metaphor in general

Metaphor is allowed only when the figure is precise and the literal meaning is unavailable or much longer. The default is literal description.

If the writer reaches for a metaphor, the writer should first ask: what is the literal thing I am describing? Write that instead.

| Bad | Better |
|---|---|
| The skeleton of the house. | The foundation, load-bearing walls, and primary load path. |
| Route the service parts so they can change. | Design mechanical and electrical runs for access and replacement. |
| The real game. | (cut entirely; whatever follows is the actual point) |

## What The Voice Avoids

- personification of inanimate things
- aphoristic closers and quotable lines
- antithesis structures (X is not A, it is B)
- definition by negation
- rule-of-three rhythm and rhetorical triplets
- anaphora used for cadence
- persuasive headings
- blockquote pronouncements
- decorative intensifiers
- compound serial lists for completeness signaling
- persuasive openers and thesis sentences
- concession-then-correction pivots
- metaphor where literal language exists
- emotional language applied to objects
- cute, jolly, whimsical, or sentimental tone
- dramatic flourish
- scolding
- nervous hedging
- fake empathy
- corporate-safe prose
- vague motivational language
- generic summaries
- em dashes
- excessive bullets
- buzzwords and stock AI phrasing

Avoid phrases such as: delve, tapestry, realm, landscape, it is important to note, ultimately, not just X but Y, crucial, pivotal, robust, seamless, leverage, foster, elevate, navigate, transformative, journey, unlock, empower, embrace, ecosystem.

## Risk and Problem Pattern

Name the issue. State the next step.

Use plain language for both. Avoid figurative phrases like "cleaner path," "way through," "down the road," or any other figure that turns an action into terrain or motion.

Acceptable opening phrases for the issue:

- "One issue is..."
- "A common failure is..."
- "The risk is..."
- "Before [action], check that..."

Acceptable opening phrases for the next step:

- "The next step is..."
- "The fix is..."
- "To prevent this, ..."
- "If this happens, ..."

Every risk passage must end with an action the reader can take, a person to call, a record to save, an alternative to choose, or a check to perform.

Bad:

> Improper installation can lead to serious problems.

Better:

> One issue is poor bracing. Forms can spread during placement, which can bow the wall or move anchor bolts. Before the truck arrives, walk the forms, check corners and openings, and tighten any weak bracing.

## Project Cleanup

Reader-facing manuscript text must not mention prior drafts, source material, revision history, how the book was developed, what an earlier session did, or "current manuscript" commentary. Preserve the knowledge, not the editing trail.

The manuscript must not contain the old project acronym. Sentences that contain it require natural rewriting around the house, the project, the concrete home, the owner-builder, or the specific system.

The long-life goal applies to the parts that are difficult or destructive to replace: the foundation, the structural concrete, the major load path, and similar elements. Roofs, mechanical equipment, plumbing parts, electrical equipment, smart-home devices, finishes, sealants, and windows are designed for maintenance and replacement on shorter cycles.

If an inherited idea seems strange, outdated, or possibly abandoned, ask the user before expanding it as final direction.

## Reader Layers

The book uses a four-layer system, also called the Knowledge Ladder. The layers are `Simple`, `Applied`, `Professional`, and `Code`. Each layer is written for a different reader and answers a different question.

| Layer | Reader | What it answers | What the reader can do after reading |
|---|---|---|---|
| `Simple` | A friend or family member with no construction background | What is this system, and why does it matter in this house? | Describe the system in their own words |
| `Applied` | The owner-builder, a capable DIY-engineer-scientist for whom budget and creativity are the practical limits | What do I physically do, in what order, with what verification? | Perform the work tomorrow, or know exactly what is needed to learn it |
| `Professional` | Builders, designers, engineers, building officials, and inspectors | What design mechanism, parameter, tolerance, or coordination rule controls this work? | Hold a substantive design conversation with the owner-builder |
| `Code` | Anyone verifying compliance | Which statute, rule, code section, standard, or listing controls this, and what does it actually say? | Verify compliance without opening the official code book in most cases |

The layers are different kinds of content, not four registers of the same paragraph.

Layers are not a quota. Use the layers that add value in a given section. Using all four is fine when each earns its place. Using one or two is fine when the others would repeat the same information in different words. Decide section by section.

The book is meant to substitute for the official code book wherever possible, for the systems and details actually being built in this house. `Professional` and `Code` blocks should carry enough content that the reader does not need to open ORSC, OPSC, OESC, OMSC, ASCE, ACI, ASTM, TMS, ASHRAE, NFPA, or other referenced sources for routine verification. The official sources are still the legal authority; the book is the working reference.

### Simple

Ordinary words. Explains what the thing is and why it matters.

If a term such as `subgrade`, `differential settlement`, `hydrostatic pressure`, `load path`, `active zone`, or `modulus` is needed, either explain it in plain language or move the idea to another layer.

Simple is usually short. A few clear sentences are enough.

### Applied

Action.

Use verbs the reader can perform: walk, dig, mark, measure, photograph, call, schedule, test, label, save, stop, verify, document, install, protect, inspect.

Avoid abstract instruction verbs in Applied: consider, evaluate, assess, approach, recognize, keep in mind, take into account.

If the reader cannot perform the action tomorrow morning after reading the block, Applied has failed.

### Professional

Real trade depth. The vocabulary a trade professional, designer, or engineer would recognize as useful.

Use specific terms when they matter: allowable bearing pressure, settlement, Plasticity Index, active-zone depth, hydraulic conductivity, lateral earth pressure, seismic design category, cover, lap length, development length, diaphragm, collector, chord, vapor drive, pressure drop, voltage drop.

Professional must add a mechanism, parameter, calculation, tolerance, or design decision. Professional written as Applied with longer sentences is filler. Skip the layer instead.

### Code

A `Code` block lists the controlling sources and explains what each one actually says, in enough detail that the reader does not need to open the official code or standard for routine verification.

Format: each citation begins on a new line in colon format. After the colon, give a short description of the rule, the table reference, the limit, the geometry, the test method, the inspection trigger, or other context the reader needs. Multiple lines per citation are allowed and often appropriate. Do not paraphrase copyrighted code text; describe what the section controls.

Example, short form:

```
ORSC R401.3: drainage around foundations. Required slope of 6 inches in the first 10 feet from the foundation. Surface drainage must be directed away from the building.
ASTM E1745: standard for plastic vapor retarders used below concrete slabs. Class A, B, and C designations differ in physical durability; Class A is the strongest. ORSC R506.2.3 requires a 10-mil ASTM E1745 Class A retarder under habitable-space slabs in Oregon.
```

Example, longer form when the rule warrants it:

```
ORSC R403.1.6: anchor bolt requirements for sill plates.
  - Minimum 1/2-inch diameter anchor bolts, embedded 7 inches into concrete.
  - Maximum spacing 6 feet on center for one-story; 4 feet on center for two-story in SDC D2.
  - Bolts must be located within 12 inches of plate ends.
  - 3-inch by 3-inch by 0.229-inch plate washers required between sill plate and nut.
```

A `Code` block must contain at least one of:

- an Oregon specialty-code section (ORSC, OESC, OPSC, OMSC, OSSC)
- an Oregon statute (ORS) or administrative rule (OAR) citation
- a referenced standard (ASTM, ACI, ASCE, ASHRAE, NFPA, UL, ANSI, TMS, or similar)
- a code table number with the table's working content
- an official form, named agency source, or jurisdictional program reference
- a manufacturer listing, label, or installation standard
- an inspection trigger tied to a code section or permit condition

A `Code` block that only says to verify locally, check with the building department, consult a professional, or follow approved plans is not a `Code` block. Add the controlling source and what it requires, or skip the block.

Do not invent citations. If a citation is needed and cannot be verified, mark the line for research rather than fabricating.

Code editions change. When the rule depends on the edition in force, name the edition (for example, "2023 ORSC, effective October 1, 2023, mandatory April 1, 2024") so the reader knows when the cited content was current.

## Layer Shape

A reader skimming the page should see the difference between layers without reading the labels.

| Layer | Page Shape |
|---|---|
| `Simple` | Short prose, ordinary words, little formatting. |
| `Applied` | Steps, checklists, action tables, field checks, records. |
| `Professional` | Denser technical prose, parameters, units, mechanisms. |
| `Code` | Citation list with short descriptions. |

Drafting order for technical sections, when useful:

1. What does the owner-builder physically do?
2. Which sources control or verify the work?
3. What mechanism or parameter does a professional consider?
4. What plain explanation helps a non-builder understand the point?

This is a drafting order, not a required page order.

## Surrounding Text

The four-layer system carries the bulk of the technical content. Around the layer blocks, supporting text holds each section together and adds the context, comparisons, and decisions that do not fit cleanly inside any single layer.

Use surrounding text only when it earns its place. Sometimes a section needs none. Sometimes it needs several supporting elements. The categories below are available; they are not required.

| Category | Purpose |
|---|---|
| Chapter overview | A short orientation at the start of each chapter that names the topic, the function of the chapter, and the related material handled by other chapters by topic name |
| Section topic statement | One or two sentences naming what the section is about, before any layer block |
| Decision matrix | A table that drives a choice across multiple criteria when the decision does not fit inside a single layer |
| Comparison table | A side-by-side comparison of materials, methods, products, or approaches |
| Design-rationale note | A short, named explanation of why a particular choice was made for this house |
| Make-vs-buy discussion | Comparison of purchasing, fabricating, or owner-making a component, when more than one path is real |
| Equipment list | Specific gear with specifications, not generic descriptions |
| Cost framing | Real-dollar ranges for the work, with the year of the estimate noted |
| Field-failure-mode panel | A short list of typical mistakes, how they show up, how they get caught, and how they get corrected |
| Inspector-readiness summary | What the inspector looks for at the relevant gate, what gets cited, what counts as a correction notice |
| Records-to-save list | What goes into the project binder from the section's work |
| Cross-reference note | Where another chapter handles an adjacent topic, named by topic, never by chapter number |
| Glossary preview | A short plain-language note on a defined term used in this section, with the full entry living in the glossary |
| Photo or sketch prompt | What to record at this stage of the work, with what reference scale and what label |
| Pre-cover or pre-pour checklist | The checks that happen before the work disappears |
| Tolerance table | The dimensions, clearances, and limits the work has to meet |
| Code-edition note | When a value depends on the edition in force, the edition is named |
| Worked example | A specific scenario walked through start to finish with real numbers |
| Build-sequence note | When the work has to happen relative to other trades and inspections |
| Site-pattern note | Regional Oregon patterns when they affect the design or construction |

The four-layer system is the central content. Surrounding text is well-placed support, not padding. If a category does not earn its place in a section, leave it out.

## Chapter References

Do not refer to book chapters by number in running text. Use the chapter name or topic.

Do not write previous-chapter or next-chapter transition sentences. The chapter order may change. Cross-references must survive reordering.

External source references such as NEC chapters, ORSC chapters, OAR chapters, ASHRAE chapters, ACI chapters, and other standards are unaffected by this rule.

## Chapter Endings

Do not write closers, summaries, callbacks, or quotable final lines.

A chapter ends when the information ends. A checklist ends after the last check. A procedure ends after the last step. A technical explanation ends after the source, tolerance, inspection point, or decision is clear.

If the writer feels the urge to write a final sentence "to wrap up," delete that urge and the sentence.

## Practical Construction Style

Active construction verbs: mark, measure, excavate, compact, form, brace, align, square, tie, chair, lap, place, pour, vibrate, screed, float, cure, seal, flash, anchor, inspect, verify, document.

Use bullets when the reader needs to scan tools, steps, risks, inspection points, tolerances, responsibilities, or common mistakes. Use prose when explaining why something matters.

Use checklists only for items someone can physically verify with eyes, tools, documents, measurements, photos, or records.

Bad checklist item: Ensure quality construction.

Better:

- Forms are straight, plumb, braced, and clean.
- Reinforcement matches the approved structural drawings.
- Required cover is maintained with chairs or spacers.
- Sleeves, embeds, anchor bolts, and blockouts are installed before the pour.
- Inspection approval is recorded before concrete placement.

Repetition is acceptable for safety, sequencing, inspection gates, code compliance, curing, waterproofing continuity, structural drawing compliance, and common failure points. Repetition is not acceptable as a rhythm device. A repeated warning must add a new failure mode, inspection point, or action.

Do not use em dashes. Use periods, commas, colons, parentheses, or shorter sentences.

## Specificity Over Fluff

Replace vague advice with observable action.

| Bad | Better |
|---|---|
| Proper site preparation is important for a durable foundation. | Strip topsoil, remove organic material, compact the subgrade, and verify bearing conditions before placing forms or reinforcement. |
| Moisture management is very important. | One issue is water at cracks, joints, penetrations, and below-grade walls. To prevent this, plan drainage, waterproofing, capillary breaks, flashing, and sealants before concrete is placed. |
| Reinforcement should be properly installed. | Install reinforcement as shown on the approved structural drawings. Check bar size, spacing, lap length, cover, chairs, dowels, embeds, and openings before inspection. |

Numbers help. Specific products help. Named code sections help. Real measurements help. When prose feels thin, add a number, a product name, a code section, or a measurement before reaching for any other tool.

## Authority and Uncertainty

Do not invent code requirements, engineering values, structural capacities, reinforcement sizes, footing dimensions, fire ratings, wall thicknesses, span limits, mix designs, or waterproofing claims.

Use sources accepted for the chapter: Revision 2, Revision 3, user research files, verified web research when requested, official code sources, approved plans, manufacturer instructions, professional design documents.

Hedge only when uncertainty is real. A rule that varies by jurisdiction, code edition, soil condition, seismic category, wind exposure, product listing, or engineered design must say so. A plain fact must not be weakened to sound cautious.

Good: The footing depth depends on the local frost-protection path and the approved foundation design.

Also good: Topsoil does not belong under structural concrete.

## Forms and Records

Do not display fill-in forms in the manuscript. Forms can be discussed, named, referenced, and described, but blank forms must not appear.

Records the manuscript should direct the reader to save: permit approvals, inspection results, correction notices, product data, manufacturer instructions, photos before cover, batch tickets, test results, field decisions, professional letters.

## Standing Lessons

1. Preserve knowledge. Remove duplicated expression, not unique information.
2. Let chapter function shape the writing. Orientation, reference, procedure, legal, business, glossary, and technical chapters do not need to sound identical.
3. Use the four layers only where each adds value.
4. Draft technical `Applied` content early so the section starts from real work.
5. `Code` blocks name specific sources and explain what each one says, in enough detail that the reader does not need to open the official code book for routine verification.
6. `Professional` blocks need real trade depth or stay silent.
7. Keep `Simple` plain enough for a curious non-builder, and never use metaphor as a shortcut.
8. Avoid reader-facing revision history.
9. Use the colon format for citations.
10. Never personify inanimate things.
11. Never use the rhetorical performance patterns listed in this file.
12. Default to plain literal description in every layer.
13. The book is meant to substitute for the official code book where possible. Bigger and more thorough is better when the added content is useful, well organized, easy to read, and benefits the builder. Bigger for its own sake is not.
14. Reference other chapters by topic, never by number. Chapter order may change.
15. First person is allowed where it earns its place. The default is impersonal.

## Pre-Submission Check

For items 1 through 13 and 16 through 19 below, the answer should be no. For item 14, 15, and 18, the answer should be yes.

When checking, do not stretch to find a problem that is not there. If a check passes cleanly, the check passes cleanly.

1. Does any inanimate noun in the chapter take a human action?
2. Does any sentence in the chapter exist primarily to sound quotable?
3. Does any section use antithesis (X is not A, it is B)?
4. Does any sentence define something by what it is not before saying what it is?
5. Does any heading make a claim or argument instead of naming the topic?
6. Does any blockquote elevate the writer's own sentence rather than quote a source?
7. Does any list contain three items chosen for rhythm rather than count?
8. Does any sentence begin with the same phrase as the previous sentence for cadence?
9. Does any sentence contain a decorative intensifier (truly, deeply, real, actual, simply, very, quite)?
10. Does any sentence use a metaphor where literal language would be the same length or shorter?
11. Does any compound serial list exist to signal completeness rather than enumerate real items?
12. Does any section open with a thesis sentence rather than a statement of topic?
13. Does any section end with a closer, summary, callback, or quotable line?
14. Does each layer used in the section add information distinct from the others?
15. Does every `Code` block cite a specific source and explain what the source says?
16. Does any sentence expose the book's revision history?
17. Does any internal reference rely on chapter numbers, previous-chapter, or next-chapter language?
18. Does every risk passage end with a concrete next step?
19. Does the old project acronym appear anywhere?
20. Does any first-person passage exist where impersonal voice would be cleaner?

## Compact Working Prompt

Write a technical reference manual for an Oregon owner-builder building a concrete home. The book is meant to substitute for the official code book wherever possible. Treat the reader as a capable adult.

Use plain literal language. No metaphor anywhere. No personification. No aphorisms. No antithesis. No definition by negation. No rule-of-three rhythm. No anaphora. No persuasive headings. No blockquote pronouncements. No decorative intensifiers. No compound serial lists. No persuasive openers.

Use the four-layer system (`Simple`, `Applied`, `Professional`, `Code`) only when each layer adds value. Audience definitions:

- `Simple` — friends and family with no construction background; plain words, no metaphor, fun-to-read but straight-to-the-point.
- `Applied` — the owner-builder, a capable DIY-engineer-scientist for whom the only practical limits are budget and creativity.
- `Professional` — trade depth: real terms, mechanisms, parameters, tolerances.
- `Code` — controlling sources with their content explained, enough that the reader does not need to open the official code book.

For risk passages: name the issue, then state the next step.

Default to literal description. Add specifics, numbers, product names, and code sections before reaching for any other tool.

First person is allowed where it earns its place. Default is impersonal.

Reference other chapters by topic name, never by number.
